# Multi-Document Intelligence Workbench

A local full-stack demo for uploading several documents, extracting a small set of facts, and comparing those facts with traceable evidence. All included sample data is synthetic.

## Quick start

Requirements: Node.js 24+ and npm (the server uses Node's built-in SQLite module).

1. Copy `.env.example` to `.env` and adjust values if needed.
2. Set `OPENAI_API_KEY` in `.env`; the default model is configurable with `OPENAI_MODEL`.
3. Install dependencies with `npm install`.
4. Start both services with `npm run dev`.
5. Open http://127.0.0.1:5173 and upload files from `samples/`.

The API uses port 3001 by default and SQLite creates `workbench.sqlite` on first run. `npm run build` produces the frontend bundle; `npm start` runs the API and serves that bundle when `dist/` exists. `npm test` runs the included automated test.

## Deploying to Render

Create a Node Web Service from this repository with build command `npm ci && npm run build` and start command `npm start`. Render supplies `PORT`; the server listens on all network interfaces and serves the React build and API from the same origin. The free web service filesystem is ephemeral, so the SQLite database and uploaded analysis records can reset after a restart or redeploy. Use a persistent database/storage setup before relying on deployed records.

## Architecture

- `src/client`: React + TypeScript single-page interface, file upload, prompt entry, provenance display, and copy action.
- `src/server`: Express + TypeScript API, in-memory upload handling, PDF/text/CSV ingestion, local fact extraction, OpenAI Responses API analysis, and SQLite persistence.
- `src/shared/types.ts`: shared contracts for facts, sources, findings, and documents.
- `src/server/analysis.ts` and `src/server/parsers.ts`: document-scoped parsing and local fact extraction. `src/server/llm.ts` calls OpenAI with separated document records and schema-constrained JSON output, then checks citations against the source text.
- `samples/`: synthetic application and accounts examples with an intentional licence and revenue mismatch.

## Assumptions and completed functionality

- Supported inputs are PDF, TXT, and CSV. PDF text extraction uses `pdf-parse`; scanned/image-only PDFs need OCR and return a readable error.
- Analysis uses OpenAI's Responses API and requires `OPENAI_API_KEY`; `OPENAI_MODEL` defaults to `gpt-6.2-astra`. The local key-value fact extractor is pattern-based, while summaries, comparisons, and discrepancy interpretations are generated by the LLM.
- Users can upload up to 10 files per request, 10 MB each by default, list them, remove them, issue a natural language instruction, inspect extracted facts per document, see sourced findings, and copy the structured JSON output.
- OpenAI returns structured findings with source IDs and quoted excerpts. The server rejects citations that do not match a supplied document excerpt. Model interpretations can still be wrong and need human review.
- An upload batch is fully validated and parsed before database writes begin; all rows are inserted in one SQLite transaction, so an invalid later file does not leave earlier files saved.
- Uploads are held in memory only and extracted text/facts are saved to SQLite. The demo does not persist original uploaded file bytes.
- Documents larger than 200,000 extracted characters are capped for analysis; the interface now marks documents that were capped.
- The request prompt is recorded with each result; analysis is re-run over all currently stored documents.

## AI and decision disclosure

This reference implementation was created with Codex. The implementation decisions made here include calling OpenAI's Responses API for analysis, keeping each uploaded document as an independent database row and request input object, validating the LLM's structured output and source excerpts, and storing uploads in memory rather than on disk. Document text is sent to OpenAI for analysis; the Responses request sets `store: false`. A candidate adapting this project should disclose the AI development tools they actually used and identify which architectural and implementation decisions they made personally.

## Known limitations

- Local key-value extraction uses supported patterns; the LLM can reason over supplied text but may miss or misinterpret arbitrary details. Missing-information findings are not guaranteed, and equivalent values such as `$1 million` and `$1,000,000` may still be compared incorrectly.
- Model output is probabilistic and source-quote checks do not prove that an interpretation is correct. Keep a human reviewer in the loop.
- CSV files are ingested as text, not interpreted as typed tables. There is no image OCR, chunking, background job queue, auth, or per-user data isolation.
- Database rows store extracted content without a retention policy. The app is intended for local synthetic-data evaluation only, not real customer or banking documents.
- Local development uses the Vite API proxy. In production the frontend calls the same-origin API, and the server binds to all interfaces for the host proxy.

## Security considerations

- File names are reduced to basenames and are never used as disk paths. The server uses memory storage, a format allowlist, file/count limits, prompt validation, text truncation, and parameterized SQL.
- Never upload real customer/banking data to this demo. For production, add authentication and authorization, tenant-scoped database access, malware scanning, stronger content validation, encrypted storage, data deletion/retention controls, rate limits, audit logging, secret management, and privacy review.
- Do not treat extracted facts or generated interpretations as authoritative. Evidence excerpts are shown so a reviewer can verify them against the source.

## Productionisation

For production, use managed PostgreSQL for relational data and persistent object storage for original files. Add OCR for image/scanned documents, page-aware chunking and retrieval for large files, asynchronous processing, retries and observability, authentication, tenant isolation, retention/deletion workflows, and a comprehensive test suite. Keep evidence-grounding checks and human review for high-impact decisions.

## Automated test

`src/server/analysis.test.ts` verifies that revenue is extracted, conflicting values are flagged, and each value remains associated with its originating document. Run it with `npm test`.
